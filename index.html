Comprendre

Comment marche un LLM

Pas de maths. Juste le modèle mental qu'il faut pour prompter juste : ce qu'il prévoit, ce qu'il oublie, ce qu'il ne fait pas.

Mécanique

Il ne « comprend » pas : il prédit le mot suivant

💡 Conséquence directe
Il choisit le token le plus probable, pas le plus vrai. Une suite plausible n'est pas une suite correcte : c'est la racine des hallucinations.
Le contexte décide

Le même mot, deux sens — « avocat »

🥩 Un mot n'a pas UN sens figé
Pour le modèle, le sens d'un mot dépend des mots autour. « avocat » bascule selon le contexte — et donc la suite qu'il prédit aussi.
🥑 « J'ai mangé un avocat… »
Suite probable : bien mûr, à la cuillère. → le fruit.
VS
⚖️ « Mon avocat plaide… »
Suite probable : demain au tribunal. → le métier.
💡 Pourquoi ça compte pour vous
C'est pour ça que le contexte que vous donnez change tout : le modèle ne devine pas votre intention, il la déduit des mots présents. Contexte clair = bonne piste.

Transformer 2/3

Self-attention : tout le contexte compte

Pour chaque token, le modèle pondère l'importance de TOUS les autres tokens du contexte avant de décider quoi prédire ensuite.

👑 Contexte = roi · Garbage in = Garbage out
Ce que vous mettez dans le prompt influence directement la sortie. Un contexte propre donne une sortie propre ; un contexte pourri donne une sortie pourrie. C'est ce qui change tout vs les anciennes architectures (RNN, CNN).
Garbage in

Mauvais contexte → sortie médiocre

Prompt vague, sans rôle ni contraintes. À copier-coller dans GPT-5.5 :

fais une fonction qui calcule des trucs sur les comptes
🔎 Résultat (en direct)
On l'exécute maintenant — zone à observer pendant la démo.
Garbage out... évité

Bon contexte → sortie exploitable

Même besoin, contexte précis (rôle, objectif, signature, contraintes, format). À copier-coller dans GPT-5.5 :

calculerInterets(double solde, double tauxAnnuel, int jours)
qui retourne les intérêts simples (exemple fictif, aucune donnée réelle).
Ajoute la JavaDoc et 2 cas de test JUnit.

Comment il apprend

Pré-entraîné, puis affiné — 3 leviers

🧠 On n'écrit pas ses règles — on l'entraîne, puis on l'adapte
Du général au sur-mesure, trois techniques que vous croiserez partout :
📚
Transfer learning
On part d'un modèle qui a déjà « tout lu » (le pré-entraînement) et on réutilise ce savoir — on ne repart jamais de zéro.
🎯
Fine-tuning
On le spécialise sur un jeu d'exemples ciblé : un domaine, un style, une tâche précise.
👍
RLHF
Des humains classent ses réponses ; il apprend à produire ce qu'on préfère (utile, clair, poli).
⚠ Le piège du RLHF
Il apprend à plaire, pas forcément à dire vrai — d'où la sur-confiance et la flagornerie. (On creuse au chapitre « niveau expert ».)

💭 Une question

Si la fenêtre est immense, autant tout y déverser ?

À votre avis ?

✅ La réponse

Non : plus de contexte n'est pas mieux

💡 Grande fenêtre ≠ tout y mettre
Deux raisons. D'abord la pertinence : noyé sous le bruit, le modèle pondère moins bien les tokens vraiment utiles — la sortie se dégrade (garbage in, garbage out). Ensuite le coût : on paie chaque token d'entrée, donc un prompt gonflé = une facture gonflée. Le bon réflexe reste un contexte minimal et propre, pas maximal.
Limite

Le coût se compte en tokens

💰 On paie au token
En entrée (votre prompt) et en sortie (la réponse). Prompts longs = factures longues.

Réflexe de dev : un contexte minimal et propre, ce n'est pas que de la qualité — c'est aussi du budget.

Limite

La coupure des connaissances

⚠ Knowledge cutoff
Le modèle est entraîné jusqu'à une date donnée. Il connaît mal ou pas du tout ce qui est arrivé après cette coupure.

Une librairie sortie le mois dernier, une API récente : il peut l'ignorer — ou inventer une version plausible.

Limite

Pas de déterminisme garanti

Une fonction Java
Mêmes entrées → toujours la même sortie.
VS
Un LLM
Même question → réponse parfois différente.

La génération est probabiliste : ne comptez pas dessus comme sur un calcul exact reproductible.

Démo

Exagérer le hasard : à tester en direct

Prompt à lancer 3 fois de suite dans GPT-5.5 (puis en jonglant : raisonnement profond / normal / une version antérieure) :

Invente un nom de code original pour un projet bancaire,
en un seul mot, puis explique-le en une phrase. Sois créatif.
🎲 À observer (en direct)
Même prompt, plusieurs exécutions → réponses différentes. Le déterminisme n'est pas garanti ; le réglage (température, mode) change l'ampleur de la variation. Côté culture : temperature = degré de créativité / aléatoire, top_p = diversité du vocabulaire, max_tokens = longueur (et donc coût) de la réponse.
Attention

Ce qu'un LLM ne fait PAS

  • Garantir l'exactitude de ce qu'il affirme
  • Comprendre votre intention au sens humain
  • Accéder à votre code interne (sauf intégration explicite)
  • Inventer des connaissances qu'il n'a pas vues sans halluciner
  • Garantir la même réponse à la même question
  • Apprendre de votre conversation au-delà de sa fenêtre de contexte

💭 Une question

Pourquoi tous les assistants de chat et de code sont-ils decoder-only ?

À votre avis ?

✅ La réponse

Parce qu'ils complètent du texte

💡 Génération = prédire le token suivant
Un decoder-only est entraîné à prédire le token suivant et à continuer une suite de texte : c'est exactement ce que demandent le chat et la complétion de code. Les encoder-only (BERT) sont taillés pour classer ou rechercher, pas pour générer ; les encoder-decoder (T5, BART) visent surtout traduction et résumé. Pour produire du texte ou du code librement, la famille decoder-only est la plus directe.
Maturité

Modèle « base » vs « instruction-tuned »

Modèle de base

La matière brute, issue du pré-entraînement. Il complète du texte, il ne « répond » pas. Peu utilisable tel quel pour une appli.

VS
Instruction-tuned

Entraîné à suivre des instructions puis aligné. C'est ce qu'on utilise tous les jours : ChatGPT, Claude.ai, le Chat...

Comment on le fabrique

De la matière brute au modèle « obéissant »

1
Pré-entraînement → modèle de base : on entraîne sur d'énormes volumes de texte à prédire le token suivant. Il apprend la langue, des faits, du code... mais il ne fait que continuer le texte.
2
Fine-tuning supervisé (SFT) : on l'entraîne sur des paires instruction → bonne réponse. Il apprend à répondre, pas seulement à continuer.
3
Alignement (RLHF / préférences) : des humains classent les réponses ; le modèle est ajusté pour être plus utile, honnête et sûr. → instruction-tuned.
💡 À retenir
Les modèles que vous utilisez sont des modèles de base alignés. C'est cet alignement qui les rend « obéissants » — et qui explique aussi pourquoi ils refusent parfois.

1 · Raisonnement

1 · Raisonnement

Quand l'activer — et ce que ça coûte

⚡ Modèle rapide suffit
Lookup, reformulation, CRUD, classification, réponse factuelle courte. Inutile de « faire réfléchir ».
🧠 Activer le raisonnement
Debug multi-étapes, refactor d'archi, planification, analyse/calcul. Là, le brouillon paie.
💰 Le surcoût (ordre de grandeur)
Les tokens de réflexion sont facturés comme de l'output — comptez ~2 à 5× l'usage. Et « plus de réflexion » n'est PAS toujours mieux (overthinking) : sur une tâche simple, ça coûte sans rien gagner.
⚠ Bank-safe
Les tokens de réflexion partent chez le fournisseur comme tout prompt (mêmes règles no-paste). Le « raisonnement » affiché peut être tronqué/résumé — ce n'est pas un log d'audit fiable.
2 · Embeddings

L'espace de sens — quand les mots deviennent des coordonnées

📍 L'analogie GPS
Un embedding, c'est les coordonnées d'un mot (ou d'un texte) sur une carte. Deux sens proches = deux points proches. Concrètement pour un dev : un float[1536] (1536 dimensions chez OpenAI, 3072 pour le gros modèle).
📐
Similarité cosinus
On compare l'angle entre deux vecteurs : 1 = même sens (voiture/automobile), 0 = sans rapport. La direction porte le sens, pas la longueur.
🔍
Fondation du RAG (J2)
Recherche sémantique = embedder la question, chercher les vecteurs proches. Trouve « gel des avoirs » même si l'on tape « blocage de compte » — là où LIKE '%mot%' échoue.
⚠ Idée fausse
Le fameux roi − homme + femme ≈ reine est en partie un artefact (l'astuce d'exclure les mots d'entrée). Bonne intuition pour comprendre — pas une preuve mathématique.

4 · Hallucination

Pourquoi il invente — avec aplomb

🎓 L'analogie de l'examen
Un LLM est un étudiant à un QCM noté 0/1. Laisser blanc = 0 garanti ; deviner = une chance d'avoir juste. Sur tout l'examen, deviner bat l'honnêteté — le modèle a appris à bluffer.
🧠 Le vrai mécanisme (OpenAI, sept. 2025)
L'hallucination n'est pas un bug du Transformer : c'est un problème d'incitations. L'entraînement et les benchmarks récompensent une réponse fausse mais confiante plutôt que « je ne sais pas » (la grande majorité des évaluations).
⚠ Calibration
Confiance affichée ≠ vérité. Un ton assuré n'est jamais une garantie — surtout en banque.
4 · Hallucination

Les 4 parades (bank-safe)

🤷
Autoriser l'abstention
Dans le prompt : « réponds je ne sais pas si tu n'es pas sûr ». On retire la prime au bluff.
📚
Grounding / RAG
Ancrer la réponse sur des sources (doc interne). Limite : le RAG hallucine encore parfois — pas magique.
🔗
Exiger des sources
Demander une référence vérifiable. Pas de source = signal d'invention. « Montre-moi », pas « fais-moi confiance ».
✅
Vérification systématique
Relecture + tests + un second passage. Le dev senior reste le vérificateur.
📝 Le réflexe
Sur un livrable CA Titres, toute sortie LLM = un brouillon non vérifié. L'IA propose, l'humain valide avec un outil.

Dense vs MoE, et le multimodal natif

Dense
Chaque token passe par tous les neurones (toute l'équipe lit chaque ticket).
VS
Mixture-of-Experts (MoE)
Un routeur n'active que 2-3 « experts » par token. Cabinet de spécialistes + standard.
🧠 Capacité ≠ calcul
Ex. DeepSeek-V3 ≈ 671 Md de paramètres au total mais ~37 Md activés par token. On entraîne énorme, on infère « petit » — d'où l'économie qui fait que quasi tout le frontier 2026 est MoE. Revers : il faut toute la RAM. Idée fausse : « MoE = plusieurs modèles » → non, un seul, activation creuse.
📺 Multimodal natif
Un seul modèle entraîné sur texte + image + audio (pas un OCR collé à un LLM). Il « voit » et « entend » nativement.

  • Un bench peut être abandonné par ses propres auteurs — OpenAI a cessé d'utiliser SWE-bench Verified (« ne mesure plus la capacité frontière », contamination)
  • Contamination / data leakage — si le test était sur le web avant l'entraînement, le score gonfle (mémorisation, pas raisonnement)
  • Saturation — sur MMLU-Pro, top modèles agglutinés ~90 % avec ~13 pts de variance selon la méthode : « 89 vs 88 » est dans le bruit
  • Classements Elo (LMArena) ≠ vérité — biais de style (réponses longues, confiantes gagnent) ; loi de Goodhart : la mesure devient une cible
🎯 Choisir un modèle en expert — 4 axes, pas un palmarès
Tâche · latence · coût · souveraineté. Le seul vrai juge : votre jeu de test (200-500 cas réels, fictifs côté CA) avant de figer un défaut.

Du prompt risqué au prompt sûr

Technique 1

Placeholders & pseudonymisation

🏷️ Le principe
Remplacez chaque donnée sensible par un jeton neutre avant le prompt. Vous gardez la structure, vous perdez le secret.
❌ Brut
client Dupont, ISIN FR_DEMO_0001, 1 200 titres
→
✅ Pseudonymisé
CLIENT_X, ISIN_PLACEHOLDER, QTE = N
Technique 2

Abstraction du cas

🧮 Le principe
Ne décrivez pas VOTRE cas réel : décrivez un cas générique équivalent. Le LLM résout le même problème technique sans jamais voir votre métier.
  • « Un écran qui passe un ordre de bourse » → « un formulaire qui valide une commande avec quantité et code produit »
  • Le bug, la logique, la structure restent identiques
  • Aucun terme métier sensible ne sort de la banque
Technique 3

Extraction du pattern sans le secret

🔍 Le principe
Isolez la question technique pure. Vous ne demandez pas « corrige mon code » avec tout le contexte : vous extrayez le pattern (regex, algo, structure) et vous le posez seul.
// Au lieu d'envoyer tout le service avec les données réelles :
« Quelle regex valide une chaîne de 12 caractères
  alphanumériques en majuscules ? »
// Le pattern résolu, vous le recâblez vous-même en interne.

À votre avis ?

✅ La réponse

Les trois se combinent, selon ce qui fuite

💡 Une question, pas un menu
Ce ne sont pas trois options exclusives. Placeholders quand la structure doit rester (un ISIN, un montant) mais que la valeur est secrète. Abstraction quand c'est le métier qui trahit (ordre de bourse → commande générique). Extraction quand seule la question technique compte (une regex, un algo). Sur un vrai cas, on les empile : c'est exactement ce que montre le slide suivant.

Acte 7

Le cadre bancaire

🛡 L'esprit du chapitre
Des garde-fous, pas de la peur. L'IA générative est un outil puissant mais imparfait. En banque française, trois choses structurent son usage : ce qu'on n'envoie jamais, ce qu'on vérifie toujours, et le cadre légal qui explique pourquoi.
Règle no-paste

Les 5 réflexes de confidentialité

  • Pas de code dans les LLM web.
  • Pas de logs, tickets ni données réels.
  • Pas de secrets, clés API ni identifiants.
  • Pas d'architecture interne détaillée.
  • Toute sortie IA est relue, testée et contextualisée avant usage réel.
⚠ La règle qui résume tout
Si le prompt envoyé tel quel à un inconnu révélait quelque chose de confidentiel, c'est qu'il ne doit pas partir. On abstrait d'abord.
Secret bancaire

Art. L511-33 CMF

Tout établissement est tenu au secret professionnel sur les informations confidentielles de ses clients. Concrètement, pour un dev :

  • Jamais de numéro de compte, nom de client ou transaction dans un LLM externe.
  • Jamais de schéma de base de données avec des données réelles.
  • Jamais de code qui afficherait des données client soumis à un LLM.
⚠ Ce n'est pas une option
Le secret bancaire est une obligation légale, pas une bonne pratique interne. C'est la raison d'être de la règle no-paste.

Hallucination

Plausible mais faux

🧠 Définition
Une réponse plausible mais factuellement fausse, produite avec assurance par le LLM.

Trois causes principales :

  • Le modèle prédit ce qui « ressemble » à une bonne réponse, sans vérifier.
  • Il n'a pas le contexte nécessaire, mais ne le dit pas.
  • Les données d'entraînement contiennent des erreurs.

La réponse compile dans la tête, pas dans le compilateur. La vérification se fait dans la Javadoc officielle, pas sur la confiance du modèle.

RGPD

Une donnée personnelle dans un prompt

Le RGPD s'applique dès qu'un prompt contient une donnée à caractère personnel (DCP) :

  • Nom, prénom, email, téléphone d'une personne identifiable.
  • Identifiant client unique, adresse IP, cookies traçants.
  • Données sensibles : santé, opinion politique, religion (art. 9 RGPD).
⚠ Règle simple
Si le prompt contient une DCP, il ne part pas dans un LLM externe — sauf consentement explicite, base légale validée par le DPO, ou anonymisation préalable irréversible.
